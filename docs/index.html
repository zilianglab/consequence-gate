Consequence Gate
Agent governance · demo walkthrough

What being wrong costs, not how sure the model is.

Consequence Gate sits between an agent and its tools and decides whether each call may run — by resolving it into one of four autonomy tiers.

Below: what the tiers mean, how a single call gets decided, and what actually happened in the three demo runs — the same runs whose terminal output was hard to read, told visually.

The wrong question
“How confident is the model?” Reading a ticket and deleting an account have similar success rates. Confidence can’t tell them apart.
The right question
What does being wrong cost, who absorbs it, and how long before anyone notices?
01 — the vocabulary

Four tiers of autonomy

Every call lands in exactly one. They run from “just do it” to “never, regardless of confidence.” In the run panels below, each call carries its tier as a colored stripe.

[ OK ]
execute
Run it and log it. Reversible, contained — no one needs to look.
[ OK ]
execute_notify
Run it, but surface it for review. Costly to undo, so it doesn’t happen silently.
[ HOLD ]
propose
Prepared but held. A human must commit before it executes.
[ STOP ]
refuse
Out of scope, full stop. No confidence level unlocks it.
more autonomy → less autonomy

03 — the one rule that makes it work

Confidence can make the gate stricter, never looser.

↓ low confidence

Pulls a call toward less autonomy — a reversible action drops from execute to “surface it.” The gate gets more cautious.

↑ high confidence

Buys nothing. It can’t lift an irreversible action out of “a human commits,” and it can’t buy past a policy floor.

Mechanically, confidence appears in the resolver in exactly one place: a below-threshold tightening bump. There is no branch anywhere that loosens as confidence rises — so the claim is a property you can test, not a promise.

05 — reading the gate

Metrics, and the number not to chase

All computed from the audit log across the three runs — nothing hardcoded. These are illustrative of what each metric means, not a calibration sample: the figures below come from just three scripted runs (escalation precision is 1 of 3 stopped calls), so read them as a worked example, not as tuned defaults.

76.9%
task completion rate
33.3%
escalation precision (1 of 3 stopped) — of what it stopped, what a human actually rejected
14.3%
cost-weighted error rate — mistakes weighted by consequence, not counted
~3µs
gate overhead per call (p50) — essentially free next to the tools

Completion rate is the trap. It rises as you loosen the gate, so an org that optimizes it will optimize the gate away. Escalation precision and cost-weighted error pull against each other and have to be read together — tighten the gate and error falls, but so does precision. Neither alone tells you if the gate is set right.
